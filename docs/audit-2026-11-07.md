# Migration audit — 7 November 2026

Independent review of the move from browser-only storage (IndexedDB) to accounts backed by Django and PostgreSQL. It covers the code in the working tree, the plan in [implementation-plan.md](implementation-plan.md) and [design.md](design.md), and the claims in [project-state.md](project-state.md). It recommends an order for the remaining work.

## Verdict

The server foundation is real. Accounts, campaigns, field-level privacy, path-level saves, private images and personal notes all exist, and every check re-run in section 2 still passes. The critical risk is not code quality. **Twenty days of work across three milestones (90 files) is uncommitted in this one working tree.** The second problem is that the actual character sheet UI does not use the server yet. Remote mode runs a separate, plain form UI. No milestone in the plan covers moving the real UI onto the server.

The plan says milestone 4 (GM library) is next. This audit recommends against that order. Commit the work, add CI, then make the real UI and minimal admin screens work against the server, deploy a thin staging copy early, migrate real data, and only then build the library.

## 3. Findings

### Critical

**C1. All migration work is uncommitted.** The backend, storage layer, remote client, tests, `AGENTS.md` and `docs/` exist only in this working tree, last touched 18 October. One disk failure, a careless `git checkout .` or `git clean`, or an AI Studio sync that touches the same files would lose it. Nothing is on GitHub. Section 5, step 0, gives the safe way to checkpoint it. The repository is public and Vercel-connected, so the push needs care.

**C2. The real UI does not run on the server.** `src/main.tsx` picks one of two separate applications at build time: `App` (the full sheet, local/mock only) or `RemoteApp` (a generic registry form). The full UI saves whole records about 60 times in `CharacterDetail.tsx` alone. That is exactly the pattern the design forbids for remote data, because hidden fields would be lost. Two further gaps make reuse harder:

- **Shape mismatch.** Local `complicaciones`, consequences, aspects and `teachingSubjects` are plain string arrays. The server needs `{id, value}` items. Local images are embedded base64; the server uses asset UUIDs. Local `CustomField` and some `Skill` items have no IDs.
- **Mock mode does not use the server contract.** AI Studio previews `MagistriScholaeMockDB` complete records. Every new UI feature built there adds more whole-record code that will have to be converted later.

The handoff noted this on 18 October as a "recommended integration task". It is not yet in the plan, and it is the largest remaining piece of work.

**C3. Nobody can onboard users without raw API calls.** The site administrator can only be created with `createsuperuser`. Creating a campaign, issuing a GM or player invitation, issuing a reset code and disabling an account are API-only. These need a CSRF token and a session, so in practice the owner would use curl or a browser console. Admins also have no endpoint to list users, yet a reset code needs the user's UUID (`POST auth/reset-codes {userId}`). The only way to find a UUID is to be a GM of a campaign containing that user, or to use the Django shell.

### High: deployment defects already in the code

These do not affect local development. Each would break or weaken the first real deployment.

| # | Defect | What happens | Fix |
|---|---|---|---|
| H1 | No `SECURE_PROXY_SSL_HEADER` (settings say "no proxy-header trust") | Behind a reverse proxy that terminates TLS, Django believes every request is plain HTTP. `SECURE_SSL_REDIRECT` then loops forever. If the loop is avoided, the CSRF origin check compares `https://…` to `http://…` and rejects every mutation, including login. | Set `SECURE_PROXY_SSL_HEADER` for the known proxy only, and have the proxy overwrite (not append) `X-Forwarded-Proto`. |
| H2 | Rate limits keyed on `REMOTE_ADDR` (`accounts.login_account`, `views.register`, `views.password_reset`) | Behind a proxy every request has the proxy's address. The per-IP limits become site-wide: 100 logins, 30 registrations and 20 reset attempts per 15 minutes for everyone combined. One person spamming the login form locks out the whole group. | Derive the client IP from the trusted proxy's forwarded header, ignoring client-supplied values. |
| H3 | No `LOGGING` setting | With `DEBUG=false`, Django's default console handler only runs when DEBUG is on, and the email handler has no `ADMINS`. Server errors (500) leave no traceback anywhere. An app server's access log would show at most the 500 status, because Django turns the exception into an ordinary response. | Log `django.request` and the app to stdout at WARNING and above, without request bodies. |
| H4 | No production packaging | `requirements.txt` has no WSGI server (gunicorn or similar). There is no Dockerfile, production Compose file, proxy config or static-file plan. | Part of the thin staging step (section 5, step 4). |
| H5 | Old data is tied to the browser origin | Players' current records live in IndexedDB under `https://magistrischolae.fyi`. Only code served from that exact origin can read them. A staging hostname cannot. After DNS moves to Contabo, the old Vercel build lives only at a `*.vercel.app` address, a different origin. If the new app does not include a reader for the old database, any player who did not export a file beforehand cannot easily reach their data. The remote build currently contains no Dexie code (checked in the built `dist/assets/*.js`). | Ask every player to export a backup file from the current site before cutover. Also ship a read-only legacy reader plus a dry-run import screen in the new app at the production origin. |

### Medium

- **M1. Read-only endpoints take write locks.** `media.download` and the GM-note GET call `sheet_for(..., lock=True)` inside a transaction. That is `SELECT … FOR UPDATE` on the campaign row. Every image request queues behind every save in the campaign. Remote mode shows no portraits in lists today, so the effect is small now. Once the real list UI shows avatars it will matter. Lock only for mutations.
- **M2. List requests make many small queries.** Each projected sheet repeats membership, role, share and bond lookups. Estimated from the code (not measured), a 50-item page makes a few hundred queries. That is fine for one group, but cache the viewer's membership per request before lists grow.
- **M3. Any membership change makes every open editor conflict.** `set_membership` bumps `campaign.policy_revision`, which is part of every sheet's revision token. If the GM adds a player mid-session, every player's next save returns 409 and shows the conflict screen. This is by design, but the UX needs a plan: auto-retry when the refreshed projection is unchanged, or bump only when it affects that viewer.
- **M4. `SECRET_KEY` is also the key for every HMAC.** It hashes invitation tokens, reset codes and rate-limit keys, signs revision tokens and fingerprints retry receipts. Rotating it after a leak silently invalidates outstanding invitations and reset codes, makes every open editor conflict, and turns in-flight retries into `operation_reused`. Django's `SECRET_KEY_FALLBACKS` does not cover these custom HMACs. Use a separate HMAC key setting and document a rotation procedure.
- **M5. Tables and files grow without limit.** `ProcessedOperation` gets a row for every mutation. `AuditEvent`, `RateBucket`, Django database sessions and detached image files also accumulate. Add a maintenance command (including Django's `clearsessions`) and schedule it in deployment.
- **M6. No CI.** Codex and AI Studio both edit this repository, and the contract-drift and boundary tests only help if they run. There is no `.github/` directory.

### Low

- **L1.** These dependencies are not imported anywhere in `src/`, `tests/`, `scripts/` or `vite.config.ts`: `@google/genai`, `express`, `@types/express`, `dotenv`, `motion`. They may be AI Studio template leftovers. Confirm before removing. The package is still named `react-example`.
- **L2.** `RemoteApp.tsx` line 219 uses `window.confirm` to delete a personal note. The local UI deliberately avoids it because it is unreliable inside sandboxed iframes such as AI Studio previews.
- **L3.** The known skill-preset key mismatch remains. `CharacterDetail` writes `magistri_default_skills_preset`; the form and factory read `fate_wizardry_custom_default_skills`.
- **L4.** The main `App` chunk is 502.6 kB. Splitting `CharacterDetail` during the integration work (step 2) would fix this naturally.
- **L5.** Per-username login throttling runs before authentication. Anyone who knows a username can lock that account out for 15 minutes with 10 bad attempts. This is acceptable for an invite-only group. Note it in the support runbook.
- **L6.** Stale lines in `design.md`. Line 3 says "Milestones 1–2 are implemented"; milestone 3 is also done. Line 99 says the storage interface, mocks and backend "have not yet been implemented". Line 407 says the lockfile and `.env.example` are absent; both now exist.
- **L7.** The remote UI code packs many statements onto very long lines (for example `RemoteApp.tsx` lines 120–130). It works, but it is hard to review and risky for AI tools to edit. That matters because this code is security-relevant UI.

### What is good and should be kept

- Server-side projection with absent (not blank) hidden fields, allowlisted path patches, viewer-bound revision tokens, and no whole-record PUT. The hardest privacy rules are already enforced in one place: `backend/domain/permissions.py`.
- Every campaign mutation locks the campaign row first. This gives a single lock order that avoids deadlocks, and concurrency tests run on real PostgreSQL, not SQLite.
- Retry receipts with operation IDs that store fingerprints, not response bodies. The client save queue retries the exact same request after an uncertain failure.
- Mode selection is explicit, with no silent fallback from remote to local or mock.
- The field registry is generated from the server, with drift tests.
- Personal notes are a separate table that never appears in GM responses, and promotion is atomic.
- Old local data and the backup format are preserved, and the old defects are reproducible with `test:baseline`.

## 4. Evaluation of the plan

**What the plan gets right.** Django and PostgreSQL suit the privacy model. Milestones are small with explicit evidence. Local mode is preserved. "Hidden is not blank" is treated as a first-class rule. Deployment is kept separate from code. Milestones 1–3 followed the plan and the evidence holds up.

**Where the plan needs correcting.**

1. **It measures progress by backend features, not by a usable product.** Milestone 3, "remote editing", counted as done with a stopgap form. After milestones 4 and 5 as written, the GM library and offline snapshots would also only be reachable through that stopgap. Integrating the real UI should be its own milestone, before more server features.
2. **Admin and onboarding screens belong to no milestone.** "Full administration/disclosure UI remains ahead" appears in several places but is never scheduled. Without it, launch is impossible.
3. **Deployment comes last, so infrastructure bugs surface last.** H1–H3 are invisible on loopback. The design (section 16) already allows staging checkpoints. Use one early, with fictional accounts.
4. **The scope is large for "one private group with one GM".** Most of the privacy machinery is already built and should stay. The GM library with per-field sync baselines (milestone 4) is the most complex remaining feature and the easiest to defer until real use shows it is needed.
5. **The working method left a large uncommitted batch.** Each milestone was verified carefully, but none was committed. Future milestones should end with a commit and a pull request.
6. **The documentation is thorough but verbose and partly stale.** `project-state.md` collects history (two pause records and three checkpoints) on top of the current state. A one-screen "current state" at the top, with history below or moved to a changelog, would help the next agent and AI Studio.

## 5. Recommended path forward

Sizes are relative (S, M, L), not time estimates.

### Step 0: Checkpoint the work (S, do first)

1. Decide whether `docs/` should be public (see decision 1). It contains no secrets: `backend/.env`, `.venv`, `.tmp` and preview media are git-ignored, and a commit dry run listed none of them. Specific VPS, registrar and DNS details were later moved to the git-ignored `docs/infrastructure.local.md`.
2. Commit everything on `codex/milestone-3-remote` as **one** commit, e.g. "Add storage boundary, Django API and remote editing (milestones 1–3)". The milestones overlap in the same files (`public/sw.js`, docs, `App.tsx`), so splitting them after the fact would produce commits that never existed as working states.
3. Push **that branch only**, never `main`. Vercel will probably build a preview of the branch in default local mode, which is harmless. First confirm in Vercel which branch is production. Also check whether the newly committed `.node-version` (26.8.1) and `engines` field change the Node version Vercel uses.
4. Open a draft pull request to `main`. Do not merge until a browser check of the local app on the preview passes.
5. Delete or ignore the empty `codex/milestone-1-storage` and `codex/milestone-2-backend` labels.
6. Until this lands, AI Studio should not push to `main`.

### Step 1: CI (S)

Add a GitHub Actions workflow for pull requests:

- Frontend: `npm ci`, `lint`, `test`, all three builds, and `test:baseline` (needs `fetch-depth: 0` because it reads commit `2518abd`).
- Backend: a `postgres:18` service, then `check`, `makemigrations --check`, `export_api_contract --check` and the test suite with `config.test_settings`.

This turns the boundary and contract rules in `AGENTS.md` into something enforced, not just requested.

### Step 2: Integration milestone, one sheet UI on the server contract (L, critical path)

Goal: the existing character and familiar screens run in local, mock and remote mode against one interface.

1. **Shared sheet interface.** A hook or service that exposes `fields` (partial, server shape), `capabilities`, `edit(path, value)`, `remove(path)`, the save state and conflicts. Components never receive a complete record they could save back.
2. **Lossless converter: local record ⇄ registry v1 shape.** Gives string lists stable IDs and keeps unknown legacy fields. It needs round-trip tests on the existing fixtures. Step 5's legacy import reuses it, so it pays off twice.
3. **Three adapters.**
   - Remote: the existing `SaveQueue` and `RemoteClient`.
   - Local: Dexie records through the converter, with full capabilities. It can keep saving whole records internally, because local data has no hidden fields.
   - Projected mock: fictional fixtures in server shape, with a visible role switcher (GM, assigned player, shared reader) and simulated hidden fields, conflicts, offline state and failures. AI Studio then develops against the real contract.
4. **Convert the screens.** Turn the ~60 whole-record saves in `CharacterDetail` (and those in `FamiliarDetail`, `FamiliarEditor`, `CharacterForm` and `CharacterList`) into path edits. Render absent fields as hidden or read-only, never as defaults. Resolve image values per mode (base64 locally, `/api/v1/assets/{id}` remotely). Split `CharacterDetail` into per-tab files while doing this; that also helps AI Studio and fixes the chunk warning.
5. **Move login, registration, reset and personal notes** from `RemoteApp` into the real app shell and styles. Keep the generic registry form only as a developer or debug view, or delete it.

Done when: remote mode shows the real sheet; mock mode demonstrates GM, player and reader views; the 34 frontend tests plus new adapter and converter tests pass; a browser check covers all three modes on desktop and mobile; and no component saves a whole record.

### Step 3: Minimal admin and GM screens (M)

- **Backend:** add `GET api/v1/admin/users` (administrator only, paginated).
- **Site administrator screens:** create campaign, issue GM invitation, list users, issue reset code, enable or disable account.
- **GM screens:** members, player invitations, sheet assignment, read-only shares, archive and restore, visibility defaults and overrides with the existing preview/apply flow, GM notes.
- **Player screen:** own visibility restrictions, with preview/apply.

Done when the owner can onboard the group without curl or the Django shell (only `createsuperuser` at bootstrap).

### Step 4: Thin staging on Contabo (M; pulled forward from milestone 6)

1. Finish the read-only VPS inventory listed in `design.md` section 15.
2. Fix H1–H4, and add the M5 maintenance command.
3. Build images for Django (with gunicorn) and the static frontend. Use a production Compose file with a reverse proxy, private PostgreSQL, a media volume and `migrate` as a deliberate step.
4. Serve a staging hostname with fictional accounts only, using a separate database and media volume.
5. Set up `pg_dump` plus a media copy to an off-VPS destination, and do one restore drill on a clean environment.

Done when the staging smoke tests pass over HTTPS behind the proxy (login, edit, image, note promotion, logout), rate limits see real client IPs, a deliberate error appears in the logs, and a restore succeeds.

### Step 5: Legacy transfer (M; first half of milestone 5)

- Server import with dry run, per-item report, idempotent job IDs and the converter from step 2.
- Separate character and familiar export/import, as the owner decided.
- An in-app migration screen that, at the production origin, reads the old `MagistriScholaeDB` read-only and offers the dry run (see H5). It falls back to backup files.
- Before cutover, every player exports a backup file from the current site.

Done when copies of real backups import on staging with images, bonds and warnings intact, checked on a second browser.

### Step 6: Offline read-only snapshots (M; second half of milestone 5)

The current app works fully offline. An online-only launch is a regression for players without connectivity at the table. Owner's call whether this ships before launch (see decision 3).

### Step 7: Launch and cutover (S–M; rest of milestone 6)

Production deployment, smoke checks and the DNS switch from Vercel to Contabo as a separate, deliberate action. Keep the Vercel project and players' backup files until the owner retires them. Write a rollback and recovery runbook.

### Step 8: GM library and selective sync (L; milestone 4, after launch)

Build it once the group is using the product and the need is confirmed. The design in `design.md` section 11 stays valid.
